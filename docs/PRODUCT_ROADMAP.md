### 1.3 竞品关键洞察

**行业趋势：**

1. **实时索引已成标配** — Dify、AnythingLLM、RAGFlow 均支持文件上传后实时索引，用户无需手动触发管线
2. **Reranker 是检索质量的分水岭** — Dify 和 RAGFlow 均提供多种 Reranker 选项，显著提升检索精度
3. **多轮对话记忆是基本期望** — 所有主流产品均支持对话上下文记忆
4. **文档管理 UI 是必需品** — 用户期望通过 Web UI 管理知识库，而非 CLI
5. **分块策略多样性** — RAGFlow 以 6+ 种分块策略（含模板分块）作为差异化卖点

**Vault 的差异化优势：**

1. **格式识别深度** — 50+ 种 PRONOM 格式识别，远超竞品
2. **上下文检索增强 (Contextual Retrieval)** — Anthropic 风格的块级上下文增强，竞品均无此功能
3. **层级检索** — 文件夹→摘要→块三级检索，比竞品的扁平检索更精准
4. **本地优先架构** — 完全离线运行，无外部 API 依赖，隐私安全
5. **音视频转录** — Whisper 集成，竞品中仅 Dify 有类似能力
6. **强制引用机制** — 可配置的引用强制策略，减少幻觉

### 2.2 关键差距详析

#### Gap 1：无增量索引机制 🔴 严重

**现状：** 添加新文件需重新运行完整管线 (`vault run-all`)，包括重新哈希、格式识别、提取、分块、嵌入。对于大型知识库（1000+ 文件），这可能耗时数十分钟。

**竞品对比：** Dify/AnythingLLM/RAGFlow 均支持文件上传后秒级索引。

**影响：** 用户体验极差，无法实现"即传即查"。

#### Gap 2：Reranker 未实现 🔴 严重

**现状：** 代码中明确标注 "Reranker not implemented yet"，配置项存在但未生效。RRF 融合后的结果直接传递给生成阶段。

**竞品对比：** Dify 支持 BGE/Cohere/Jina 等多种 Reranker；RAGFlow 内置 BGE-Reranker。

**影响：** 检索精度受限，尤其在大规模知识库中，噪声 chunk 会显著降低生成质量。

#### Gap 3：无对话历史与多轮记忆 🔴 严重

**现状：** 每次查询独立执行，无上下文记忆。用户无法追问、澄清或深入探讨。

**竞品对比：** 所有主流产品均支持多轮对话，常见策略为滑动窗口（最近 N 轮）或摘要压缩。

**影响：** 交互体验远低于用户期望，复杂问题无法通过多轮交互解决。

#### Gap 4：无文件管理 UI 🟡 重要

**现状：** 知识库管理完全依赖 CLI（`vault init`, `vault run-all` 等）。无 Web UI 上传文件、浏览文档、查看提取结果。

**竞品对比：** Dify/AnythingLLM/RAGFlow 均有完整的文档管理界面。

**影响：** 非技术用户无法使用，技术用户也缺乏直观的知识库视图。

#### Gap 5：单一分块策略 🟡 重要

**现状：** 仅支持 sentence-window 分块（窗口大小 5）。无递归字符分块、语义分块、代码感知分块等替代方案。

**竞品对比：** RAGFlow 提供 6+ 种分块策略，包括模板分块（简历、论文、合同等专用模板）。

**影响：** 对代码文件、表格密集型文档、结构化报告等特殊格式，分块质量不佳。

#### Gap 6：无查询优化 🟡 重要

**现状：** 用户原始查询直接用于检索，无查询改写、扩展、HyDE（假设文档嵌入）等优化。

**竞品对比：** Dify 支持通过工作流节点实现查询改写；Mem.ai 自动进行查询优化。

**影响：** 模糊、简短或不精确的查询导致检索质量下降。

#### Gap 7：无访问控制 🟡 重要

**现状：** 所有用户看到所有文档，无认证、授权、多租户支持。

**竞品对比：** Dify/RAGFlow 支持知识库级访问控制；Notion AI 继承 Notion 的权限体系。

**影响：** 无法在企业环境中安全部署。

#### Gap 8：无外部集成 🟢 锦上添花

**现状：** 无 Slack/Teams/邮件/Webhook 集成，无嵌入式部署选项。

**竞品对比：** Dify 支持 iframe 嵌入和 Slack 集成。

**影响：** 使用场景受限，无法融入用户现有工作流。

## 三、分阶段演进路线图

### Phase P0：基础补齐（4-6 周）

> **核心目标：** 补齐现代 RAG 产品的基本能力，使 Vault 达到"可用"标准

#### P0.1 — Reranker 实现

| 项目 | 详情 |
|------|------|
| **目标** | 实现 Cross-Encoder Reranker，提升检索精度 |
| **技术方案** | 集成 `dengcao/Qwen3-Reranker-0.6B`（已配置但未实现），通过 Ollama 或原生推理 |
| **实现要点** | 1. 在 `rag/retrieval.py` 中实现 `rerank()` 函数<br>2. 对 RRF 融合后的 top-50 候选进行重排序<br>3. 返回 top-k 最终结果<br>4. 支持配置化开关 (`models.reranker.enabled`) |
| **预期效果** | 检索准确率提升 15-30%（参考 BEIR 基准） |
| **技术难点** | ⭐⭐ 中等 — 代码框架已就绪，需实现推理逻辑和批处理 |

#### P0.2 — 多轮对话记忆

| 项目 | 详情 |
|------|------|
| **目标** | 支持多轮对话上下文，用户可以追问和澄清 |
| **技术方案** | 滑动窗口策略：保留最近 5 轮对话作为上下文注入 prompt |
| **实现要点** | 1. API 层：`/query` 和 `/query/stream` 接受 `conversation_id` 参数<br>2. 新增 `conversation` 和 `message` 表存储对话历史<br>3. 检索时：用最后一轮查询检索，但生成时注入完整对话历史<br>4. UI 层：侧边栏对话列表 + 新建对话按钮 |
| **预期效果** | 用户满意度显著提升，支持复杂多步问题 |
| **技术难点** | ⭐⭐⭐ 较高 — 需数据库 schema 变更 + UI 重构 + prompt 工程 |

#### P0.3 — 文件上传与管理 UI

| 项目 | 详情 |
|------|------|
| **目标** | 通过 Web UI 上传文件、浏览知识库、查看文档详情 |
| **技术方案** | 新增 `/api/files/upload` 端点 + 前端文件管理页面 |
| **实现要点** | 1. API：文件上传（拖拽 + 点击）、文件列表、文件删除、文件预览<br>2. 上传后自动触发增量索引（见 P0.4）<br>3. UI：左侧知识库树形导航 + 右侧文件列表/预览<br>4. 支持批量上传（多文件拖拽） |
| **预期效果** | 非技术用户可用，知识库管理可视化 |
| **技术难点** | ⭐⭐⭐ 较高 — 需前端开发 + 文件处理管线集成 |

#### P0.4 — 增量索引机制

| 项目 | 详情 |
|------|------|
| **目标** | 新文件添加后自动索引，无需重跑完整管线 |
| **技术方案** | 文件系统监控 (watchdog) + 增量管线 |
| **实现要点** | 1. 使用 `watchdog` 库监控 corpus_root 变化<br>2. 检测到新文件 → 仅运行该文件的 Phase 1-4, 8-11<br>3. 检测到文件删除 → 清理对应的 DB 记录和向量<br>4. 检测到文件修改 → 重新处理该文件<br>5. API：`POST /api/pipeline/sync` 手动触发增量同步 |
| **预期效果** | 文件上传后秒级可查，大幅提升用户体验 |
| **技术难点** | ⭐⭐⭐⭐ 高 — 需保证增量与全量结果一致性，处理并发和失败恢复 |

#### P0.5 — 查询历史与搜索

| 项目 | 详情 |
|------|------|
| **目标** | 用户可以查看和搜索过去的查询记录 |
| **技术方案** | 利用现有 `query_log` 表，新增查询历史 UI |
| **实现要点** | 1. API：`GET /api/queries` (分页 + 搜索 + 时间范围)<br>2. UI：侧边栏"历史"标签，支持全文搜索<br>3. 点击历史查询可重新执行或查看结果 |
| **预期效果** | 用户可回顾和复用之前的查询 |
| **技术难点** | ⭐ 低 — 数据表已存在，主要是 UI 工作 |

### Phase P1：体验优化（6-8 周）

> **核心目标：** 提升检索质量和交互体验，使 Vault 达到"好用"标准

#### P1.1 — 查询改写与扩展

| 项目 | 详情 |
|------|------|
| **目标** | 自动优化用户查询，提升检索召回率 |
| **技术方案** | 三种策略可配置选择：1) LLM 查询改写 2) HyDE (假设文档嵌入) 3) 多查询扩展 |
| **实现要点** | 1. LLM 改写：用本地模型将模糊查询改写为精确查询<br>2. HyDE：先让 LLM 生成假设性答案，用答案做嵌入检索<br>3. 多查询：将原始查询分解为 3-5 个子查询，分别检索后合并<br>4. 配置项：`[retrieval] query_rewrite = "none" \| "rewrite" \| "hyde" \| "multi"` |
| **预期效果** | 模糊查询的检索准确率提升 20-40% |
| **技术难点** | ⭐⭐⭐ 较高 — 需 prompt 工程 + 额外的 LLM 调用延迟优化 |

#### P1.2 — 多分块策略

| 项目 | 详情 |
|------|------|
| **目标** | 支持多种分块策略，适配不同文档类型 |
| **技术方案** | 新增 3 种分块器：递归字符、Markdown 感知、代码感知 |
| **实现要点** | 1. `RecursiveChunker`: 按段落→句子→字符递归切分（LangChain 风格）<br>2. `MarkdownChunker`: 按标题层级切分，保持文档结构<br>3. `CodeChunker`: 按函数/类定义切分，保留上下文<br>4. 配置：`[chunk] chunker = "sentence-window" \| "recursive" \| "markdown" \| "code"`<br>5. 可按文件格式自动选择策略（format_policy 扩展） |
| **预期效果** | 代码和结构化文档的检索质量显著提升 |
| **技术难点** | ⭐⭐ 中等 — 算法成熟，需测试和调优 |

#### P1.3 — 语义缓存

| 项目 | 详情 |
|------|------|
| **目标** | 相似查询命中缓存，减少重复计算 |
| **技术方案** | 基于嵌入相似度的语义缓存 |
| **实现要点** | 1. 新增 `query_cache` 表：query_embedding, query_text, result_json, hit_count<br>2. 查询时先计算嵌入，与缓存比较（余弦相似度 > 0.95 视为命中）<br>3. 命中时直接返回缓存结果（跳过检索+生成）<br>4. 缓存过期策略：TTL 7 天 + LRU 淘汰<br>5. 配置：`[retrieval] semantic_cache = true, cache_threshold = 0.95` |
| **预期效果** | 重复查询响应时间从 5-10s 降至 <100ms |
| **技术难点** | ⭐⭐ 中等 — 需嵌入计算 + 相似度搜索 |

#### P1.4 — 文档预览与标注

| **实现要点** | 1. PDF 文件：使用 PDF.js 在浏览器渲染<br>2. 其他格式：将提取的 Markdown 渲染为 HTML<br>3. 检索命中时，自动跳转到相关页面/段落<br>4. 高亮匹配的 chunk 文本<br>5. 用户可添加标注/笔记，关联到文件段落 |
| **预期效果** | 用户可验证 AI 回答的准确性，深度理解源文档 |
| **技术难点** | ⭐⭐⭐ 较高 — PDF.js 集成 + 文本定位 + 标注系统 |

## 六、"本地优先"优势的深化策略

Vault 的核心差异化是**完全本地运行、数据不出域**。在功能演进中应持续强化这一优势：

| 策略 | 具体做法 |
|------|---------|
| **隐私作为默认** | 所有数据处理在本地完成，云端 API 为可选项且需明确用户确认 |
| **离线优先架构** | 所有核心功能（检索、生成、索引）在断网状态下正常工作 |
| **数据可移植性** | 支持完整知识库导出（SQLite + Chroma + 原始文件），用户可随时迁移 |
| **审计日志** | 记录所有数据访问和模型调用，满足合规需求 |
| **本地模型优化** | 针对 Ollama 本地推理优化 prompt 长度、批处理策略、KV 缓存 |
| **边缘部署** | 支持在 Mac Mini / NUC 等小型设备上运行，面向个人和小团队 |
